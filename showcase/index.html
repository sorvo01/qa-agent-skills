skills/testcase-designer

From a story to risk-ranked test cases

Builds a risk table first, picks a technique per input (boundaries, decision tables, state transitions, role matrix) and only then writes cases. Every case points to a risk and names the bug it would catch.

SIM Story: "Viewer can see but not change a project"

$ claude "/testcase-designer STORY-12, output CSV"
risk table
  R1 Viewer changes data through the API      impact H  likelihood M
  R2 Viewer sees Edit/Delete in the UI         impact M  likelihood M
  R3 Role change not applied until re-login    impact M  likelihood L
techniques  role x action matrix, deny cases first
cases
  TC-AUTH-003  P1  R1  Viewer DELETE /api/projects/:id → 403, project still exists
  TC-AUTH-004  P1  R1  Viewer PATCH with extra field ownerId → rejected, owner unchanged
  TC-AUTH-005  P2  R2  Viewer opens project → no Edit, no Delete, no bulk actions
  TC-AUTH-006  P2  R3  Admin demotes Editor → next request is denied without re-login
self-check
  ✓ every H risk has a negative case
  ✓ every role has a deny case
  ! R3: ask PO, is a 5 min token lifetime acceptable? (yes/no)

skills/autotest-builder

Automated tests that fail for the right reason

Picks the cheapest layer that still catches the bug, uses role-based locators, waits for states instead of sleeping, creates its own data and proves each test can fail before calling it done.

SIM Example spec from the repo, real run

$ npx playwright test examples/todo-flow.spec.ts
Running 2 tests using 1 worker
  ✓ todo list › user adds two todos and completes one → counter shows 1 item left
  ✓ todo list › empty todo is not added
  2 passed (3.5s)

$ npx tsc --noEmit --strict examples/*.ts
no errors

# definition of done: break it once on purpose
$ # change the expected counter to '2 items left' and run again
  ✗ Expected: "2 items left"
    Received: "1 item left"
  1 failed, 1 passed
→ the failure names the behaviour; revert

skills/perf-load-k6

A capacity number someone can decide on

Workload model before code, SLOs as k6 thresholds per journey, five profiles from smoke to soak, and a one-page result with the bottleneck and its evidence.

    http_req_duration{journey:browse}  p95=192.73ms  threshold < 500ms
    http_req_duration{journey:order}   p95=295.73ms  threshold < 1000ms
ProfileQuestion it answers
smokeDoes the script work?
loadDo we meet the SLOs at expected peak?
stressWhere does it break, and how?
spikeDo we survive a burst and recover?
soakDo we leak over hours?

skills/explore-session

Exploration with a charter and a debrief

One-line charter, three to five heuristics that fit the target, tagged notes with evidence captured on the spot, and a debrief that says what was covered and what was not.

SIM Session notes: project sharing

charter  Explore project sharing with a Viewer and an Editor in two browsers
         to discover what a Viewer can change through the UI and the API   60 min
heuristics  Roles and ownership · Repetition · Consistency

10:02 TEST  Viewer opens a shared project: Edit and Delete are hidden
10:06 BUG   bulk-actions menu still offers "Delete selected" to the Viewer
            evidence: shot-01.png, POST /api/projects/bulk-delete 200
10:09 TEST  same call with the Viewer token from the API client → 200, project gone
10:12 ISSUE CSV export as Viewer includes the private notes column: expected?
10:18 TEST  Editor and Viewer rename the same project in two tabs
10:19 BUG   last write wins silently, no conflict message
10:24 IDEA  separate charter: what changes when an Editor is demoted mid-session

debrief  covered UI + API for Viewer; not reached: invitations, audit log
         bugs: 1 × P1 (Viewer can delete), 1 × P3 (silent overwrite)
         confidence in sharing: low
skills/web3-synpress

The chain is the source of truth

Synpress drives MetaMask and the dApp, viem reads the chain. Every state-changing test ends with the receipt status and the on-chain balance, then checks that the UI agrees.

SIM Transfer test on a local Anvil chain

$ anvil --chain-id 31337 && npx synpress && npx playwright test

  5 waitForTransactionReceipt(hash)      status: reverted
  6 balance of recipient                 1000.0 ETH  unchanged
  ✗ expected receipt.status "success", received "reverted"
→ bug: UI reports success from the wallet response, not from the receipt
